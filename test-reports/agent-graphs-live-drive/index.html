    Test Report — The agent demo graphs driven live on the Rust engine¶

    The Rust Playground example now ships the five agent graphs of the Java Playground - the same JSON models, compiled unchanged by this engine (Increment 205) - with the example's own tool functions ported (src/order_book.rs, src/diagram.rs) and the agent loop crate linked. This drive ran every graph end to end on 2026-11-18 (UTC+8) through the Python pack of mercury-python (main, after its #67): the LLM helper on Claude Haiku 4.5, the built-in agent tools and the MCP binding, with Redis 7 and Neo4j 5 Community on Colima and the public Mermaid Chart MCP server. The Java engine's drives of the same graphs are the reference: docs/test-reports/agent-loop-live-drive.md, agent-tool-use-live-drive.md and agent-tools-live-drive.md in mercury-composable.

    Result in brief¶

    • Every graph answered on the Rust engine, with no change to any model. The order assistant held its refund for a supervisor, re-advised on a resume without decisions and on a bad decision, ran the approved refund, read the order book's 409 on a second attempt and offered a replacement after a refusal; the diagram assistant validated a flowchart through the pack's MCP binding and stored the image out of band; the four documents of the corpus went into the knowledge graph with every node carrying its source and nothing doubled on a second ingest; two questions were answered from the graph with sources; the research graph crawled this project's published documentation, waited for a person before writing the notes, and wrote them after approval.
    • The protocol is the Java engine's. The same correlation id carried a transaction across its suspension; a resume without decisions answered in under a millisecond of engine time; a decision for a call that was not waiting was refused by name before any token was spent and the transaction kept; a watched run streamed the node's text and the loop's events (run.start, turn.start, tool.start, tool.end, turn.end, run.end) before the result.
    • The same finding as the Java drive, in the same place. On the travel policy the loop's schema check refused one graph_ingest call as invalid and the model corrected the shape on its next turn; the call log reads invalid then ok, and the graph was loaded.
    • The graph's counts equal the Java drive's, label for label: Document 4, Party 4, Obligation 15, Rule 12, Deadline 8; PARTY_TO 8, STATED_IN 35; no node without a source. The document node did not double on the re-ingest, the key rule the Java drive added to the prompt holding.
    • The Python helper served 43 model turns; no token, prompt or page text reached a log of any process; the engine logged no error.

    Reading¶

    • The models are shared, not ported. The five JSON files are byte-identical copies of the Java example's; the Rust compiler accepted every node type, mapping and skill they use (graph.resume, graph.suspend, graph.math with RESET: and probes, f:concat with four arguments, llm.run with mode, progress, exception). What the Rust example needed was its own tool functions and the agent-loop crate as a dependency - the Java example's extensions/agent-loop jar - and diagram.store.folder in its configuration.
    • The packs do not know which engine calls them. The same Python helper, tools and binding that served the Java drives served this one, with the same configuration; the tools' logs read the same (graph.ingest 200 12 nodes, 11 relationships, file.write 200 … (create)).
    • A re-advise costs nothing. The Rust engine answered a resume without decisions and a refused decision from the restored state with no model call, as the Java engine does.
    • Not driven here: the WebSocket entry (graph.websocket.enabled) and the Node.js pack - the Java drives covered both, and nothing in this example is pack-specific beyond the peer ports.

    Reproduce¶

    # the stores (Colima or Docker Desktop)
docker run -d --name mercury-redis -p 6379:6379 redis:7-alpine
GRAPH_PASSWORD=... extensions/agent-tools/dev/graph-up.sh                # in mercury-python
# the pack (mercury-python shown; mercury-nodejs is the same with node dist/src/cli.js and ports 8087, 8089, 8090)
mercury-serve extensions/llm-helper/llm_helper.py -Dllm.model=claude-haiku-4-5
GRAPH_PASSWORD=... mercury-serve extensions/agent-tools/agent_tools.py \
  -Dtools.file.root=<a copy of examples/minigraph-playground/corpus> -Dtools.web.allow=accenture.github.io \
  -Dtools.graph.uri=bolt://127.0.0.1:7687 -Dtools.graph.write=true
mercury-serve extensions/mcp-binding/mcp_binding.py
# the engine, from this example's folder so resources/ is found
cargo build -p minigraph-playground --release
cd examples/minigraph-playground && ../../target/release/minigraph-playground \
  -Dllm.peer.port=8086 -Dmcp.peer.port=8088 -Dtools.peer.port=8089
# the drives
curl -s -X POST http://127.0.0.1:8085/api/graph/order-assistant -H 'content-type: application/json' \
  -H 'x-correlation-id: order-1002-case' -d '{"question": "My order ORD-1002 never arrived. What can you do?"}'
# then approve with the same correlation id: {"turn": <the reply's turn>, "decisions": [{"id": "<the call id>", "approved": true}]}
curl -s -X POST http://127.0.0.1:8085/api/graph/document-ingest -H 'content-type: application/json' \
  -H 'x-correlation-id: ingest-1' -d '{"document": "supplier-agreement.md"}'
curl -s -X POST http://127.0.0.1:8085/api/graph/document-query -H 'content-type: application/json' \
  -H 'x-correlation-id: query-1' -d '{"question": "Which deadlines does the supplier agreement set?"}'

    The token-free twin of this drive is examples/minigraph-playground/tests/agent_graphs.rs: the same five graphs on a scripted model, stand-ins for the tool routes and the Mermaid binding, and a RESP2 Redis double.
