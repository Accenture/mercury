**The dialect (shared with Java):** a send with `reply_to` + the
`accept: text/event-stream` event header relays a remote streaming function's segments
through `/api/event` on the one HTTP call — envelope frames (reserved SSE name
`envelope`, base64-encoded serialized envelopes, addressing cleared) for the head, the
terminals and non-text segments; raw SSE frames for text tokens. Explicit degradation:
non-streaming target byte-identical (buffered decode with the tolerant REST-error
unwrap); non-accepting caller of a streaming target → pinned 406
"Streaming function requires a caller that accepts text/event-stream"; lane exhaustion
→ pinned 503. x-ttl event header (ms, default 60s) = idle allowance both hops (client
pads +1s so the peer's in-band 408 wins). Client conformance guards: raw-first frame →
500 "Invalid event stream - missing envelope head"; transport end without a decoded
terminal → 500 "Event stream ended without eof"; trailing frames after a terminal
discarded.

**Two port idioms vs Java (same wire, Increment 93):**
1. **The EDGE decides the mode** — a streaming-capable /api/event call (Accept +
   !x-async) dispatches through the existing `stream_dispatch` with `envelope_mode`,
   inheriting the whole lane/channel/renderer/idle/cleanup lifecycle (Java binds the
   lane dynamically from inside EventApiService instead, because its holder map is
   cid-addressable). `EventApiService` became a true event INTERCEPTOR (actual Java
   parity — previously the one non-interceptor divergence) and rewires the inner
   request onto its own reply lane with the edge context id as the correlation id —
   the exact rewrite the RPC inbox makes. The two pre-existing event-over-http suites
   needed the matching interceptor registration (a plain registration's auto-reply
   races the manual reply — the 200-empty symptom).
2. **One wrap site** — the suite's first run caught a real port gap: the envelope-mode
   single-shot reply reached the caller unpacked (the generic edge rendering, not the
   packed octet-stream wire → the client's decode got non-envelope bytes → 400). Fix:
   capable-path service errors ride RAW envelopes and the edge wraps every unmarked
   lane reply into the classic wire (`wire_single_shot`). Documented divergence: the
   outer HTTP status of capable-path validation errors is 200 with the real status
   packed inside (Java mirrors it outer); the decoded caller-visible envelope is
   identical.
