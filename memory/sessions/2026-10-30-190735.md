## What was done (branch `fix/minimalist-kafka-dlq-key-registry-retry`)

- **The dead-letter key.** `KafkaRequestPublisher::publish_keyed` takes an optional key (`FutureRecord<[u8], Vec<u8>>`);
  `publish` delegates with none, so `simple.kafka.notification` stays keyless; `write_to_dead_letter` passes `message.key()`.
- **The registry retry, which this client lacked.** The Rust registry client made one attempt per lookup (`async.http.request`,
  10 s timeout, no retry in platform-core's HTTP client either), so Eric's ruling applied directly. Confluent 8.3.2's sources
  (the sources jar in `~/.m2`) gave the policy: `RetryExecutor` tries `max.retries + 1` times; it retries a `RestClientException`
  with status 408, 429, 500, 502, 503 or 504 (`RestService.isRestClientExceptionRetriable`) and any `IOException`; before retry
  `i` it sleeps `random.nextInt(ceil) + 1` ms with `ceil = min(retries.wait.ms << min(i, 30), retries.max.wait.ms)` (full
  jitter); defaults 3, 1000, 20000. Ported as `RegistryRetry` (`schema/auth.rs`, read from `schema-registry.yml` with the same
  keys; a non-numeric or negative value fails startup naming the key) and a loop in `RegistryClient::get` (`schema/registry.rs`).
  The platform's HTTP client reports network failures as statuses (connect or response timeout 408, refused or dropped 500,
  the `po.request` deadline 408), so one status predicate covers both of Confluent's cases. The bearer-token step sits inside
  each attempt, as in Confluent's `sendHttpRequest`. Jitter bits from `uuid` v4, already a dependency.
- **The guide** (`docs/guides/minimalist-kafka.md`): the random-partitioner note, *Retry and dead-letter* (key preserved; an
  outage fails the decode once the retries are spent), *Partitioning strategies* (*No record key on a publish*), *Consume* (*A
  registry outage is treated the same way*), the keys table. **One Rust-specific fact found on the way:** the id cache is
  `ManagedCache`, expire-after-write, so every schema id is fetched again `schema.registry.cache.ttl` (30 min) after its last
  fetch even while in use - an outage that outlasts the retries can dead-letter records at any time, not only after a start;
  the guide says so and notes that a longer TTL narrows the window (ids are immutable). Also the configuration reference, the
  bundled `schema-registry.yml` (a commented retry block), the port spec §7 item 13, module docs, the codec's startup line
  (`maxRetries`).
- CHANGELOG Unreleased: Changed 1 (the retry, with its upgrade note), Fixed 1 (the key), Documentation 1. `docs/INCREMENTS.md`
  Increment 191.

  the retry, a lookup against a registry that accepts connections and never answers can take about 47 s (four 10 s attempts

  exposed, by up to that much beyond the 10 s headroom. Both engines omit the decode, so this is parity; not changed.
