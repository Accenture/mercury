**The precision answer, from the redis-rs 1.5.0 source:** the lifecycle is
observable without extra machinery. The `ConnectionManager` triggers its own
reconnect exactly when a command fails `is_unrecoverable_error()` (public
API — `RetryMethod::Reconnect`), and it stores its connection as a shared
future in an `ArcSwap`, swapping in the *reconnection future* on failure. So:
(a) using the manager's own predicate as the retry condition keys the retry to
the real lifecycle event — never a server-side error like WRONGTYPE/NOAUTH;
(b) the second attempt *awaits* the swapped-in future — synchronized with the
reconnection, not racing or polling it — under its own timeout. An explicit
event feed exists (`set_push_sender`, disconnection pushes) but adds a
channel + task with no additional precision for this use. Recorded as port
spec §5 item 6.

**Implementation** (`store.rs`): `run_idempotent(description, operation)` —
one lifecycle-keyed retry for `save_route`/`get_route`/`cleanup`/
`queue_length` (SETEX/GET/DEL/LLEN). Deliberately fail-fast: `append_segment`
(ambiguous RPUSH replay = undetectable duplicate under D7),`pop_segment`
(ambiguous LPOP replay could silently discard a segment), `publish`
(best-effort by contract). Timeouts are per attempt; a timed-out attempt is
never retried (a timeout is not a connection-death signal).

**Tests** (`tests/store_bounce_recovery.rs`, 3 scenarios, first-run green):
a test-local TCP bounce proxy between the store and the double — severed
links = a server bounce, dropped listener = a full outage. Pins: every
idempotent op heals in ONE call across a bounce; append/pop fail fast then
heal on the caller's own retry (including "nothing was popped into the void");
the retry is single and bounded under a full outage (two attempts, no loop).
