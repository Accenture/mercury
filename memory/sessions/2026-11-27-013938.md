## Decisions

- **N is the timeout the command ran under, not an elapsed time - the agent's reading of "the measured timeout in
  milliseconds", stated to the maintainer, who did not change it.** The platform's `Timeout for N ms` names the
  timeout it was given, as Lettuce's `Command timed out after N second(s)` does; two timers cover one command and
  either may answer, so a configured value gives one text on every run, which a test can assert and a handler can
  match.
- **The wording is the maintainer's: `after N ms`.** It is the word of the Java engine's text and of this engine's
  `connect timed out after N ms`; the unit differs between the engines with the client library, which he accepted.
- **The classification is given the deadline.** The alternative, a 408 without a number where only the crate's
  error is known, would have kept two texts for one failure. `CommandError::classify` takes it too, so that it is
  right for any value of the type and not only for those `attempt` returns.
- **The raw failure's `Display` joins the one text; two neighbours do not.** `connect timed out after N ms` is
  another failure, and the sync-over-async store's 500 `Redis command timed out` is that store's own mapping; the
  maintainer asked about the request timeout. Both were named to him as unchanged.
- **The state store's step waits out the default 5000 ms.** An override of `redis.timeout.ms` for one request would
  have been faster, but it relies on the store reading the setting on every round trip and leaves the crate's
  timer at another value; with the default both timers run for the same time, which is the case the text is for.
- **No upper time bound in the new assertions.** A timeout proves by its status that the reply did not arrive; an
  upper bound adds no proof and fails on a slow runner, as the red run behind Increment 218 showed.
- **Clippy caught a doc comment** wrapped so that a line began with `- `, which Markdown reads as a list item
  (`doc_lazy_continuation`); rewrapped.
