## What We Did

- **The question, measured with a throwaway integration test (`crates/platform-core/tests/zz_depth_probe.rs`, deleted after each run,
  never committed).** This engine decodes untrusted MsgPack with `rmp_serde::from_slice`, in `EventEnvelope::from_bytes` and the Event
  API's `is_compact_envelope`. rmp-serde's default depth is 1,024; it decrements its counter on entering each array or map, the
  outermost included, and refuses at zero.
  - Release build: 1,023 nested arrays decoded and the 1,024th was refused ("depth limit exceeded").
  - Debug build, a 2 MiB test thread (the size of a tokio worker's stack): 500 decoded, and 600 aborted the process (`fatal runtime
    error: stack overflow`).
- **The fix, Increment 160, PR #358, twin of the Java engine's #514.**
  - `serializer::MAX_DEPTH` is 64, the outermost container being level 1.
  - `serializer::from_msgpack` (`set_max_depth(MAX_DEPTH + 1)`; `Nesting deeper than 64 levels`) now serves `from_bytes`,
    `is_compact_envelope` and the distributed-cache example's `unpack`.
  - Tests: the `serializer` cases (64 nested arrays, maps or a mix decode; 65 refused; 100,000 refused) and the envelope test (a body
    nesting 63 decodes, 64 does not).
  - Docs: a "Nesting limit" note in the envelope reference, and the claim `msgpack-nesting-limit` (37 claims). CHANGELOG item 18.
  - Gates: fmt, workspace clippy, `cargo test --workspace` (128 suites, 691 passed, 0 failed, 9 ignored), and both doc checks.
