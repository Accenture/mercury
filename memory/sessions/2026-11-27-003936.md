## The fix (Increment 218), on the maintainer's word

- **Tests first.** The test double's `BounceProxy` gained `delay_replies`, which holds the server's replies back.
  `extensions/redis-connection/tests/configured_timeout.rs`: a slow reply within the configured timeout is answered
  on the managed connection, on the single one and on a manager used directly, and a reply beyond it is a 408 at
  that time in this engine's words. The state store's contract test now reaches its double through the relay and
  has a thirteenth step. All five failed against the unchanged code, at the crate's 500 ms.
- **The change.** `RedisConfig::connection_config` and `manager_config` carry the configured timeout as the crate's
  response and connection timeout; `connect_standalone`, `connect_once`, the cluster probe and
  `RedisConfig::manager` build with them, the cluster client takes both through its builder, and the state store
  sets them on its own manager. Two timers now cover one command and either may answer at the deadline, so a timeout
  the crate reports is returned as this engine's own: `CommandError::TimedOut` in `attempt`, `ConnectError::TimedOut`
  in the connect wrapper, the state store's `Redis request timed out after N ms`. A timeout is still no lifecycle
  signal. Pub/Sub connections carry no response timeout in the crate and are unchanged; the bounce test is as it was.
