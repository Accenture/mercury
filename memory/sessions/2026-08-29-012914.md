**The pool tests caught a REAL registration race (workspace run: 503 test got 200,
~25% repro).** Root cause: the lane fill loop ran on EVERY start_http_server call —
while one test drained the pool, another test's server start was still mid-fill,
releasing fresh lanes into the drained pool. First fix attempt (fill-once via OnceLock
around registration+release) made it WORSE — deterministic 15s 408s — because lane
WORKERS bind to the runtime that registers them (this port's documented per-test-runtime
idiom: each #[tokio::test] has its own runtime and route workers die with it); a
once-only registration left later tests sending events to dead lanes. Final shape:
**re-register the lanes on every server start (rebinding workers to the current
runtime, the rest_automation idiom) while filling the POOL exactly once per process**
(OnceLock around the release loop only). Verified: pool tests 15/15 consecutive runs
green; streaming 18/18. Durable lesson: in this port, a static resource pool whose
members are ROUTES must separate the pool fill (process-once) from route registration
(per-runtime rebind) — conflating them either double-fills the pool or strands it on a
dead runtime.
