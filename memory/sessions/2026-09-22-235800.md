## Method notes

- The first note-3 design keyed the replay on the io kind (BrokenPipe ⇒ never delivered). Reading `redis-rs` 1.5.0
  killed it: `closed_connection_error()` is BrokenPipe on BOTH paths (a dead pipeline task the command never reached,
  and in-flight requests when the stream ends). The second idea, the library's `Disconnection` push, needs RESP3
  (`check_resp3!`). What was left — a heartbeat whose failed PING makes the manager reconnect ahead of the next
  command — is also what fixes the actual field symptom (the producer's first `RPUSH` after a restart).
- A test expectation was wrong, not the code: under a refused outage a command waits on the manager's reconnect
  attempts up to the command deadline (408), not a fast 503 — "fail fast" means one deadline-bounded attempt, never
  two. Asserted as `408 | 503`, `retries == 0`, elapsed < 2× timeout.
