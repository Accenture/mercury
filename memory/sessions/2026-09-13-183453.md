Shipped on branch `feat/sync-over-async-r1`:

1. **`crates/redis-test-double`** (Q2's ruling made real): the in-process RESP2
   double lifted unchanged out of `minigraph-state-redis/tests/common`, now a
   `publish = false` workspace member both Redis-backed crates dev-depend on —
   two copies can never drift. Extended exactly as the spec predicted: a
   `StoredData` enum (Text | List) with `RPUSH`/`LPUSH`/`LPOP`/`LLEN` (an
   emptied list deletes its key, as a real server does), standalone `EXPIRE`,
   and **Pub/Sub** — the one structural change, a per-connection mpsc outbound
   lane plus a shared channel→subscribers registry, so `PUBLISH` can push

   `WRONGTYPE` fidelity and `SET`/`EXISTS`/`FLUSHALL`. The existing state-store
   suites kept compiling untouched (they only ever read `expires_at` /
   `contains_key`), switching `mod common;` to `use redis_test_double as
   common;`.
2. **`extensions/sync-over-async`** (`mercury-sync-over-async`, Q4): segment,
   store, both registries, coordinator, responder, config, connection. Both
   deliberate deltas landed as designed — `pipe().atomic()` (MULTI/EXEC) in
   place of Java's Lua append-with-TTL, and an explicit Pub/Sub
   reconnect/resubscribe loop with a recovery pass (one final drain per open
   stream, one queue check per pending request) that redis-rs does not provide.
   Java's atomic slot-reservation dance collapses into the registries' map
   mutex: the capacity check and the insert happen under one lock, so
   oversubscription is impossible and a rejected registration inherently
   consumes nothing.
3. **The suite**: all 13 E1 scenarios (exact ordering, three-producer
   interleave, any-producer close, orphan, consumer-side close, missed wake-up
   healed, final drain recovers a dropped close, quiet-stream drain, duplicate
   wake-ups, capacity, sink failure, the degenerate one-shot, shared return
   channel) plus 21 unit pins (segment envelope incl. cross-engine value
   tolerance, both registries, config defaults, settings). Workspace `cargo fmt
   --check`, `clippy --all-targets -D warnings` and `cargo test --workspace`
   all clean. No Docker anywhere.

**Finding (recorded in spec §3 item 8, applies to BOTH engines): a terminal
post's return value is racy by construction.** 12 of 13 scenarios passed on the
first run; `sequential_producer_delivers_in_exact_order` failed under parallel
load and passed in isolation. Cause is not a port defect: the segment is
appended store-first, so an in-flight drain (woken by an earlier post) can pop
the terminal segment, deliver it, and close the rendezvous — deleting the route
— before the producer's own route check runs. `post` then answers `false`
although the segment *was* delivered. The contract still holds ("false = stop
producing", and a producer has nothing to send after a terminal segment), but
liveness must not be asserted on a closing post. The Java E1 suite asserts
exactly that in five places and is a latent flake there — reported to Eric. The
Rust suite asserts liveness on DATA posts (where a `false` would mean lost
tokens) and pins the outcome for terminal posts.

Deliberately NOT in R1, per the spec's gate: `StreamBridge`/`EventStreamSink`,
`soa.redis.health`, and the demo — they belong to R2/R3 with the facade and the
SSE e2e, mirroring the Java E1/E2 split.

Release-time note for whoever cuts the next version: both Redis-backed crates
now carry a **path-only dev-dependency** on the unpublished double. Cargo drops
version-less dev-dependencies when publishing, so `cargo publish` stays fine for
`mercury-minigraph-state-redis` (already on crates.io) and for the new
`mercury-sync-over-async` — but the published crates' test targets will not
build for downstream consumers, which is the normal trade and worth a glance at
release time.
